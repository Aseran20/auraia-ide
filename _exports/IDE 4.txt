● ★ Insight ─────────────────────────────────────
  - VS Code's npm run watch recompiles vscode/src/**/*.ts incrementally (~2-5s
  per save) but does not watch patches/user/*.patch — the patches are only
  consumed at prepare_vscode.sh time. So during iteration, you edit the compiled
   tree (vscode/src/...) directly, then promote to a patch once it works.
  - agent-browser connects via CDP (port 9222) and persists the connection in
  ~/.config/agent-browser/session.json, which is why subsequent calls don't need
   --cdp 9222 — but only if you ran agent-browser connect 9222 once first in
  this session.
  - Ctrl+R in the dev window does a full window reload (cheap, ~1s). For changes
   to main-process code (Electron bootstrap, src/main.ts), you need to fully
  quit + relaunch code.bat because the main process doesn't reload on Ctrl+R.
  ─────────────────────────────────────────────────

  Loop par issue (le pattern à répéter pour chaque ligne du TODO)

  1. LOCATE     → Grep "texte visible" dans vscode/src/    (5s)
                   → identifie le .ts à modifier
  2. EDIT       → Edit tool sur vscode/src/...            (instant)
                   → watch recompile (2-5s, regarder Terminal 1)
  3. RELOAD     → agent-browser press "Ctrl+R"             (1s)
  4. VERIFY     → agent-browser snapshot -i                (2s)
                   → agent-browser screenshot dev/check.png
                   → Read l'image, compare avec attendu
  5. ITERATE    → si pas bon, retour à 2.
  6. PROMOTE    → Une fois validé visuellement :
                   cd vscode && git diff -- src/path/file.ts >
  ../patches/user/arclen-issueN.patch
                   → bash check-patches.sh   (valide que le patch s'applique
  propre)
  7. COMMIT     → git add patches/user/arclen-issueN.patch + commit

      165 +## File encoding gotcha — CRLF/LF mismatch breaks Edit tool   
      166 +                                                              
      167 +Some files in `vscode/src/` have **mixed line endings** (CRLF 
          +mixed with LF). The `Edit` tool's `old_string` matcher operate
          +s on the on-disk bytes, but the `Read` tool normalizes for dis
          +play — so a string you copy from `Read` output may not match t
          +he file's actual bytes.                                       
      168 +                                                              
      169 +**Symptom:** `Edit` returns "String to replace not found" on a
          + string you can literally see in `Read` output.               
      170 +                                                              
      171 +**Diagnose:** `sed -n 'Np' file | cat -A` — look for `^M` betw
          +een visible chars (not just at line end). Past incident: line 
          +`const BUILTIN_ANNOUNCEMENTS: AnnouncementEntry[] = [];` had b
          +ytes `[\r]\r;` not `[];`.                                     
      172 +                                                              
      173 +**Workarounds (in order of preference):**                     
      174 +1. **Use a longer `old_string` with anchors** that ARE pure AS
          +CII on both sides of the weird bytes.                         
      175 +2. **Fall back to Python via Bash** with a regex that tolerate
          +s the weirdness:                                              
      176 +   ```bash                                                    
      177 +   python3 -c "                                               
      178 +   import re                                                  
      179 +   p = 'path/to/file.ts'

      181 +   new = re.sub(rb'\nconst BUILTIN_ANNOUNCEMENTS:[^\n]*\n', b'
          +\n', data)

  Post-mortem — pourquoi j'en ai chié, et comment ça se corrige

  1. J'ai assumé que npm run watch faisait l'emit

  Ce qui s'est passé : j'ai lancé npm run watch, attendu 3 minutes son init
  complète (extensions cleanup + start watch sur ~25 modules), puis attendu une
  recompilation, puis constaté que out/gettingStarted.js était toujours daté de
  16:14 (l'ancien transpile).
  Pourquoi : j'ai pris pour acquis le pattern VS Code générique "watch =
  recompile incrémental". Je n'ai pas lu package.json AVANT de lancer la
  commande. Si j'avais grep "watch": d'entrée de jeu, j'aurais vu
  useEsbuildTranspile=false quelque part dans la config et compris que c'était
  un no-op.
  Remédiation (déjà dans skill) : la skill hook-development dit maintenant
  explicitement que watch ne fait que du type-check ici, et que l'emit = node 
  build/next/index.ts transpile. Le SessionStart hook le mentionne aussi dans
  NEXT_STEP.
  Règle générale pour moi : sur n'importe quel repo, avant de lancer un npm run 
  X, lire le contenu du script dans package.json. C'est 1 grep, ça économise 5
  minutes.

  2. J'ai fait un git diff naïf pour générer le patch

  Ce qui s'est passé : git diff dans vscode/ m'a renvoyé un patch de 22 lignes
  qui ne contenait pas mon vrai changement (la suppression des announcements) —
  juste deux blank lines + un changement de subtitle complètement orphelin
  venant d'un autre user patch.
  Pourquoi : j'ai assumé que la baseline de vscode/ était "post base patches
  appliquées". En réalité, prepare_vscode.sh clone upstream pristine
  (987c959751) et applique TOUS les patches comme modifications uncommitted.
  Donc git diff = upstream → état actuel = base + windows + user + mes edits,
  tout mélangé.
  Remédiation (déjà dans skill) : nouvelle section "Generating user patches —
  the tricky part" qui explique les 3 voies (.disabled rename, hand-write,
  intermediate clean state) et pourquoi git diff direct ne marche pas.
  Règle générale pour moi : sur tout repo de patches/forks, vérifier l'état git
  de l'arbre patché AVANT de faire un diff. git log -1 + git status me l'aurait
  dit immédiatement.

  3. J'ai itéré sur les erreurs TS au lieu de cascader d'avance

  Ce qui s'est passé : 3 cycles compile → erreur → fix → recompile, parce que
  j'ai retiré uniquement les call-sites puis découvert un par un que la méthode,
   les fields, le type, et la const étaient orphelins. Avec mon vrai loop à 25s
  par itération (watch encore actif), c'est ~75s perdues.
  Pourquoi : pattern de pensée "fix the immediate error" au lieu de "model the
  dependency graph". Vraiment paresseux pour un changement aussi mécanique.
  Remédiation (déjà dans skill) : section "Cascade-delete dependency tree" avec
  la checklist (type → const → fields → méthode → callsites → imports). Pour
  toute suppression de feature, je dois mapper l'arbre AVANT d'éditer.
  Règle générale pour moi : quand je supprime une feature qui touche ≥3 layers
  (type/state/method/callsite), faire un grep du symbole racine et mapper la
  cascade avant d'éditer. Pas "edit-compile-fix".

  4. J'ai été surpris par les CRLF mixés

  Ce qui s'est passé : Edit a retourné "String to replace not found" sur const 
  BUILTIN_ANNOUNCEMENTS: AnnouncementEntry[] = []; alors que Read me le montrait
   clairement. J'ai dû cat -A puis fallback Python.
  Pourquoi : ce fichier a des \r intercalés dans la ligne ([\r]\r;),
  probablement séquelle d'un Edit antérieur qui a écrit du LF dans un fichier
  CRLF. Read normalise pour l'affichage, donc je voyais []; mais les bytes
  étaient différents.
  Remédiation (déjà dans skill) : section "File encoding gotcha" avec workflow
  sed -n 'Np' file | cat -A pour diagnostiquer + fallback Python regex template.
  Règle générale pour moi : si Edit échoue sur une string qui semble visible,
  diagnostiquer bytes-level immédiatement (1 commande sed), pas tâtonner. Et sur
   ce repo en particulier, le mix CRLF/LF est endémique — je devrais m'y
  attendre par défaut.

  5. Méta-leçon : agent-browser reconnect après Ctrl+R

  Ce qui s'est passé : screenshot a renvoyé os error 10060 après le Ctrl+R, j'ai
   dû reconnect.
  Pourquoi : reload = la page entière disparait + nouvelle WS → l'ancienne
  session CDP du wrapper est invalide pendant ~1s.
